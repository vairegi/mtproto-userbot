WHY (three stacked breaks from diagnosis):
  1. Frontend never called the endpoint — Ryan's Render log showed 6
     gallery opens with ZERO /suggestions requests (WebView held a
     pre-v12.34i bundle; this zip ships the current detail-sheet.js).
  2. Pre-v12.46 the engine returned [] through the broken libsql driver.
  3. The v12.34k engine SELECTed 2,000 FULL payloads into Python to score
     — the mem_hrana_response pattern. Replaced with SQL-level scoring.

THE ENGINE (similar_sql.py — operator spec exactly):
  * Weighted scoring inside ONE SQL query per stage via json1:
    +10 artist/parody/group/character, +2 content tags. Noise metadata
    tags stripped (translated/rewrite/extraneous ads/sample/incomplete/
    missing cover/replaced/scanmark/watermarked); language & category
    buckets never scored (separate tag_groups keys).
  * Stage A: LIKE-prefiltered (high-tier names, ESCAPE'd, cap 4000)
    candidates -> json_each COUNT(*) scoring -> score DESC, favorites
    DESC, LIMIT 8. Python sees <= 8 rows x 6 scalar fields. RAM flat.
  * Stage B (deeper-scan fallback): if < 4 results, re-run with
    content-tag LIKE prefilter, excluding IDs already returned.
  * Stage C: still < 4 -> same artist (else category) by favorites DESC,
    top up to 8 — the row almost never renders empty again.
  * All values bound parameters; "group" json path quoted (reserved word).
  * A builder arg-ordering bug (prefilter args bound after score args
    while prefilter placeholders sit textually earlier) was caught by the
    live test and fixed before shipping.

VERIFIED LIVE on production Turso before ship: Stage A returned 8 scored
rows in ~1.2-1.5s on gallery:675415 and character-tier gallery:671070;
E2E ladder on 3 cached galleries (675415, 671070, 271443) each produced 8
cards with valid shapes (digit id, full-URL cover, int pages); uncached
target (537071) correctly yields empty-once-then-caches behavior.

HANDLER (scraper_bridge.py): gallery_suggestions() keeps signature,
