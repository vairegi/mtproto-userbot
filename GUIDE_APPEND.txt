WHAT CHANGED (ScraperBot only — 4 files)

1. main.py — STAGGERED STARTS. Previously db warmup (Mongo index build +
   Turso schema migration), list_sweeper, details_sweeper, and the channel
   dashboard all spawned at the same instant, so their memory peaks landed
   in the same seconds on the 512MB free instance → status-137 SIGKILL →
   Render marks instance failed → health checks time out during the next
   cold boot → repeat (the "Instance failed / Service recovered" loop on
   your events page).
   Now: db warmup starts at +5s and is SPLIT (Mongo indexes, wait 20s,
   then Turso schema), list_sweeper at +30s, dashboard at +45s,
   details_sweeper at +60s. No two peaks overlap.

2. main.py — RAM WATCHDOG. Logs VmRSS every 60s to the Render log:
   "🧠 RAM: NNN MB / 512 MB" (warn at 380MB, CRITICAL at 450MB). You can
   now see the ceiling being approached BEFORE Render kills the process.

3. app/services/telegram_bot.py — NEW COMMAND /checkram (admin only):
   replies in chat with live VmRSS, headroom vs the 512MB limit, and a
   🟢/🟠/🔴 state. Same numbers the watchdog logs. Added to /help.

4. app/config.py — dashboard default refresh 5s → 15s
   (BOT1_CHANNEL_REFRESH_SEC; per operator request). /time <n> still
   overrides at runtime.

5. app/hf_scraper_lite.py — the httpx client pool is now capped at
   4 connections (library default was 100 keep-alive connections; each
   idle keep-alive holds socket buffers that inflate RSS during bursts).

REMINDER — what UptimeRobot can and cannot do:
   It prevents Render's 15-minute IDLE spindown. It cannot stop OOM kills.
   Keep the monitor on https://scraperbackup.onrender.com/healthz (5 min,
   GET) — combined with this fix the service should now stay up.

CACHE TOPOLOGY NOTE (operator-confirmed): scraped payloads live ONLY in
Turso (BOT1_CACHE_MONGO_MIRROR=1 makes the Mongo mirror optional; with it
off, cache.py writes Turso-only). Mongo is used solely for tiny state docs
(sweep cursors, pause flag, freshness stamps, trending tags, token bucket)
in scraper1_state. There is exactly ONE copy of each cached page — no
divergence possible. New nhentai items enter the Mini App automatically:
each sweep REWRITES the whole page row (snapshot semantics), and the Mini
App reads Turso on every request (no in-memory response layer), so a
rewritten page is visible to users on the very next view.
