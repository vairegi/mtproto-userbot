v1.23.1 — THE MEMORY LEAK (ScraperBot/app/mongo_client.py)
------------------------------------------------------------
What your log showed: 76MB at boot → 334→360MB in 3 minutes of sweeping →
stuck at 463-466MB "CRITICAL" for 40+ minutes, never releasing.

Root cause (introduced by v1.22.9): the non-blocking state cache spawned
one background daemon thread per stale read/write with NO cap. The
MongoClient had serverSelectionTimeoutMS=8000 and connectTimeoutMS=8000
but NO socketTimeoutMS — so a thread performing a read on a half-dead
Atlas M0 socket could block indefinitely. Threads accumulated during every
Mongo slow phase (the 5s dashboard tick + sweeper state traffic spawn
several per minute), each pinning its stack + pymongo buffers. RSS climbed
~10MB/min and never came back.

Fixes (all in mongo_client.py):
  1. socketTimeoutMS=20000 — every blocked socket operation now dies in
     20 seconds and its thread exits. This alone stops the pile-up.
  2. _STATE_INFLIGHT guard — at most ONE background thread per state key,
     ever; repeat triggers during a slow phase coalesce instead of
     stacking threads.
  3. State-cache eviction — entries untouched for 10 minutes are dropped
     so the cache itself can never grow unbounded.

v1.23.0 — DASHBOARD COUNTDOWN + 5s refresh
------------------------------------------------------------

  message gains a next-scrape countdown suffix ("· in 2h 5m" / "· due

  by v1.22.9 + hardened by v1.23.1). /time <n> still overrides live.
