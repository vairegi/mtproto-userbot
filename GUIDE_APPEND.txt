ROOT CAUSE (verified line-by-line from the 11:23-11:25 crash log)
-----------------------------------------------------------------
NOT a leak. NOT the similar cache in RAM (the result cache lives in
Mongo-2 — 81 rows, working; the lean scan releases every doc transiently).
The crash was a PEAK-RAM collision on the 512MB instance:
  * start.sh runs THREE processes in one instance: admin_bot.py +
    worker.py (background) + uvicorn mini-app backend (foreground) —
    high baseline before any request.
  * 11:24:45-11:24:52: one /similar lean-scan completing (~15.8k docs
    streamed) PLUS a ~25-request burst (all static JS/CSS + gallery APIs)
    as a second device opened the Mini App at that exact moment.
  * baseline + burst + scan spike -> peak >512MB -> Render kill ->
    restart -> users retry -> repeat. That is why restarting "fixed" it
    for a few minutes only.

FIXES IN THIS ZIP
-----------------
1) miniapp/backend/app/db.py — NEW is_admin_user() shim. profile.py called
   db.is_admin_user(uid) but the miniapp db module never defined it (only
   the repo-root db.py had it) -> EVERY /api/profile/me returned 500 with
   "module 'app.db' has no attribute 'is_admin_user'" (visible twice in
   the crash log). Shim: super-admin id OR row in `admins` collection;
   silent-fail False on any error (profile must never 500).

2) miniapp/backend/app/services/similar_mongo.py — scan admission control.
   BoundedSemaphore (SIMILAR_MAX_CONCURRENT, default 1, env-tunable on the
   miniapp service): only one corpus scan at a time; additional cold-scan
   requests wait up to 20s then fail open (Similar row simply hides).
   An app-open burst can no longer stack scan allocations into an OOM peak.

ANSWERS TO USER QUESTIONS (for the record)
------------------------------------------
* "Page 2 loads itself on open": that is hash-restore replaying the last
  position (#search?page=2) from the previous session — by design (v12.16).
  Only ONE page is ever fetched and held (old results are replaced, never
  accumulated — that part was already correct). To force page-1 opens,
  strip the hash on boot — ask and it ships in the next zip.
* "index.html shifted in v12_64": the repo holds TWO identical copies
  (repo-root index.html + miniapp/frontend/index.html, the served one).
  Both got the app.js ?v=12.64 pin bump so they can never drift apart.
  No file was moved or renamed.
* Similar cache is NOT stored in RAM — it is a Mongo-2 document per
  gallery (similar:<gid>, 30-min TTL). Removing it was unnecessary; the
  RAM peak came from concurrent scans + boot burst, not the cache.
