SYMPTOM (your events page + log)
--------------------------------
miniapp instance killed "Ran out of memory (used over 512MB)" five times
in 25 minutes. Log window: live 10:01:47 -> dead 10:04:57 (3m10s). In that

ROOT CAUSE (my v12.60 similar_mongo.py — two compounding mistakes)
------------------------------------------------------------------
1. The scan accumulated (score, FULL_PAYLOAD) for EVERY matching gallery —
   thousands of full gallery dicts held in RAM per scan (~100-150MB).
2. The route is a sync FastAPI handler -> runs in a threadpool -> 2-3
   concurrent cold-gallery opens ran scans IN PARALLEL, stacking RAM until
   the 512MB instance was killed. Restart -> users retry -> scans fire
   again -> killed again. That is the crash loop you kept hitting.

FIXES (v12.63)
--------------
1. TOP-N HEAP SCAN: each doc is parsed, scored, RELEASED immediately; the
   heap keeps only (score, gid) for the best `limit` candidates. Winners'
   payloads are re-fetched afterwards with ONE $in query (<=8 docs).
   Peak RAM per scan: a few MB instead of ~150MB.
2. SINGLE-FLIGHT LOCK (process-wide): only one corpus scan may run at a
   time. Concurrent requests wait up to 20s for it (lean scan is ~2-4s) —
   never stack. On timeout they fail open (frontend hides the section).
3. The v12.62 per-gallery result cache is unchanged — most opens never
   scan at all.

NOT a memory leak: RAM was correctly freed between requests; the kill came
from PEAK usage during parallel scans. The fixes cap the peak.
