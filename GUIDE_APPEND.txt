ROOT CAUSE (confirmed against live Turso + Render logs + repo code)
Two bugs interacted:

1. BACKEND (scraper_bridge.py): the aggregation loop collected EXACTLY the
   requested window (page 2 → upstream pages 1+2 = 50 cards), then the
   v12.30 id-dedup removed cross-page duplicates. nhentai's volatile lists
   (popular-today, popular-week, date) reshuffle constantly, so adjacent
   pages share 5-8 galleries — 50 cards dedup to ~43. Result: short page
   (your screenshot showed only 3 cards on page 2), cushion check
   (43 > 50) False, v1.22.6 probe gated on exactly-25 items never fired,
   has_more=False → gray ›. All-time "popular" is a stable list with
   near-zero overlap, which is why ONLY it paged deep.

2. FRONTEND (search.js): highestKnownPage/knownLastPage were never reset
   on sort/query change, so browsing "popular" to page 15 leaked those
   bounds onto every other sort's numbered bar — your "browsing popular
   unlocks the other sorts" observation.

FIXES
1. Backend: collect one extra upstream page per request (collect_goal =
   want_total + per_page) so the cushion survives dedup; the lookahead
   probe now fires whenever the window is non-empty. Extra page is a
   Turso cache hit when warm — no meaningful bandwidth cost.
2. Frontend: refetch() resets highestKnownPage/knownLastPage to 0 so each
   sort learns its own bounds.
