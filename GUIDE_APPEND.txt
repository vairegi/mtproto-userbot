WHAT THE LOG PROVED
* RAM was innocent: watchdog read 76-84MB the whole time (/checkram is
  real — the numbers vary slightly between ticks; it reads
  /proc/self/status live).
* Every "Shutting down" was a graceful SIGTERM preceded by /healthz going
  unanswered — i.e. Render's 5s health check timing out, NOT an OOM.
* Between health checks the loop was stuck inside synchronous pymongo:
  state_get/state_set/is_paused run on the uvicorn event loop from
  record_activity (every fetch), _stats_bump (every write), the pause
  check (every iteration) and the dashboard tick (every 15s). One cold
  Atlas M0 socket can block up to 8s > Render's 5s window → SIGTERM →
  cold boot → cold Mongo again → loop forever (your 2-6 min cycle).

WHAT CHANGED (one file): ScraperBot/app/mongo_client.py
* state_get(): 8s in-process read-through cache. First read of a key is
  synchronous (once), thereafter stale values are served instantly while
  a daemon thread refreshes in the background.
* state_set(): updates the in-process cache IMMEDIATELY (so /pause and
  cursors stay correct for all readers in this process), then persists
  to Mongo on a daemon thread. Never blocks the loop.
* _state_fetch_sync/_state_set_sync keep the original sync behavior for
  the background threads.
Semantics: stats/cursor writes tolerate a rare dropped background write;
/pause stays exact because its cache update is synchronous.
