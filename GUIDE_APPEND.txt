## v12.40c — Bot2Fetcher paged Turso scan (2026-08-23)

### Symptom (v12.40b log)
    turso stmt error (SELECT): Resource exhausted: mem_hrana_response
    scan_cache: execute returned None
    scan: 0 candidate galleries

### Root cause
v12.40b's scan pulled `SELECT key,payload,cached_at FROM nhentai_cache`
for every gallery:* AND search:* row (~15 k rows, ~40 MB of JSON). Turso
caps a single Hrana response at ~8 MB and returned SQLITE_UNKNOWN
`Resource exhausted: mem_hrana_response`.

### Fix
`turso_store.py` split into three thin queries:
- `list_gallery_ids()`       — `SELECT "key", cached_at ... LIKE 'gallery:%'`
                               (id + timestamp only, ~7 k rows, tiny)
- `list_recent_search_ids()` — `LIMIT 200` on `search:%recent%` for the
                               newest-first seed
- `get_gallery_row(gid)`     — payload fetched on demand when a slot
                               actually claims that id

`fetcher.py` producer rewritten around the new API. libsql-client dropped
in v12.40b in favour of raw HTTP `/v2/pipeline` — no Python driver, no
version drift; same pattern as ScraperBot.

### Verified against the live DB before shipping
    gallery ids listed: 7384
    recent search ids seeded: 26
    get_gallery_row(...) OK — payload keys: id, title, title_english, ...

### Rollout
Copy `Bot2Fetcher/` over the existing folder, push, Manual Deploy.
Env unchanged. libsql-client removed from requirements.
