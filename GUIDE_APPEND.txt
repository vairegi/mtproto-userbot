## v12.40a — Bot2Fetcher turso row-parser fix (2026-08-23)

### Symptom
First deploy log:
    WARNING bot2fetcher.turso: turso execute failed (SELECT): 'result'
    INFO    bot2fetcher.fetcher: scan: 0 candidate galleries

The bot booted, connected to Mongo, authorised the userbot, then found
zero work to do and idled. Cache has 15 065 rows — should have been
7 251 candidates.

### Root cause
`turso_store.py::scan_cache` did:
    for k, payload, cached_at in rows:
libsql_client 0.3.x returns Row objects that support MAPPING access
(row["key"]) OR sequence unpacking depending on build. On the Render
instance the tuple-unpack path raised `KeyError: 'result'` from inside
libsql_client's own row wrapper, which the generic `except Exception`
swallowed as an "execute failed" warning. Result: 0 rows.

### Fix
`turso_store.py` — new `_row_to_dict(row, columns)` helper tries mapping
access first, then positional, then attribute — always returns a plain
dict keyed by column name. `execute()` now returns
`{"columns": [...], "rows": [dict, ...]}` and every caller reads by
column name, immune to the client's row-shape choices. Also decodes
bytes payloads and coerces `cached_at` safely.

### Verify after deploy
Log should show `bot2fetcher.turso: scan_cache: read 15065 rows` and
`bot2fetcher.fetcher: scan: 7251 candidate galleries`, followed by
`slot 1 claimed <gid>` and completed jobs.

### Rollout
Copy `Bot2Fetcher/` over the existing folder, push, Manual Deploy on
Render. No env changes.
