====================================================================
RENDER CPU/RAM AUDIT — mtproto-userbot / DoujinshiUniverse v12.16
====================================================================
Date: 2026-08-11
Scope: file-by-file audit of the two Render processes for the 512 MB plan.
Separate from the v12.16 pagination code — this is an ops document.

DEPLOYMENT TOPOLOGY (two separate Render services, separate processes):
  1) Mini-app backend  — FastAPI, miniapp/backend/main.py (uvicorn)
  2) Worker            — worker.py + Telethon userbot + relay_v2 + crons
MongoDB Atlas is the source of truth. Turso/libSQL over HTTP is the cache
and token-bucket store. Because the two are SEPARATE processes, no
in-memory state crosses backend -> worker; cross-process flags live in
Mongo (this is already done correctly for the v12.12+ scraper priority
queue and enable flags).

--------------------------------------------------------------------
1. HEAVY FUNCTIONS / BACKGROUND TASKS / FILES
--------------------------------------------------------------------

WORKER PROCESS (worker.py, 390 lines) spawns THREE background crons into
its own event loop at boot (worker.py:154-229):
  - prefetch_cron.run_forever()        (635 lines)  — search-page warmer
  - dedup_cron.run_forever()           (412 lines)  — Mongo dedup sweep
  - details_prefetch_cron.run_forever()(1276 lines) — per-gallery detail
        scraper, the LARGEST background task and the heaviest sleeper.

The worker also runs relay_v2.process_job() (939 lines) one job at a time
with a random 20-60s inter-job delay (worker.py:109-117, 362). Queue
consumption is strictly SEQUENTIAL — one job in flight, never two. This
is the single most RAM-friendly property the worker has.

MINI-APP BACKEND PROCESS: the heavy modules are
  - admin_bot.py          (3089 lines) — the largest single file, but it
        is the ADMIN bot (python-telegram-bot), NOT in the request path.
        It spawns two asyncio loops: _weekly_digest_loop (admin_bot.py:626)
        and _auto_queue_loop (admin_bot.py:2452). Both are long-sleep
        loops; neither is hot.
  - scraper_bridge.py     (919 lines)  — search orchestration, in the
        request path. Holds the two in-memory rate-limit dicts (see §4).
  - hf_scraper.py         (888 lines)  — nhentai JSON API client. Pure
        httpx; holds no large buffers. Response payloads are parsed JSON,
        capped by the page size (25 items).
  - db.py                 (1026 lines) — Mongo helpers. See §5 for the
        pool.

--------------------------------------------------------------------
2. CRON INTERVAL FEASIBILITY (512 MB / shared CPU)
--------------------------------------------------------------------

All intervals are env-overridable without a redeploy. Current defaults:

  prefetch_cron        TICK 5 min, per-sort sweep 6 h (popular-today can
                       be staggered to 1800s). Light: reads cache, one
                       page fetch per sort when stale. FEASIBLE.
  dedup_cron           every 12 h. Scans Mongo galleries for dupes.
                       FEASIBLE — 12 h cadence is negligible.
  details_prefetch_cron  DAY tick 60s / NIGHT tick 300s, 1 page per tick,
                       2-5s rest between gallery fetches, PAGE_CAP=30 per
                       sort, TAG_PAGE_CAP=5. Day window PAUSES when a
                       non-admin user was active in the last 300s.
                       FEASIBLE but the busiest — see §6 recommendation.
  deletion_scheduler   fixed 60s loop (deletion_scheduler.py:32). Cheap
                       Mongo poll. FEASIBLE.
  worker main loop     3s sleep on empty queue, 5s when paused. FEASIBLE.

VERDICT: no interval is too aggressive for 512 MB. The risk is not the
tick rate, it is the PEAK work per tick in details_prefetch_cron when it
hydrates a full 25-card page in one go.

--------------------------------------------------------------------
3. WORKER CONCURRENCY LIMITS / SEMAPHORES
--------------------------------------------------------------------

There are NO asyncio.Semaphore instances and NO asyncio.gather fan-out in
relay_v2.py, bot2_client.py, or admin_bot.py (grep: zero Semaphore, zero
gather). Concurrency control is by STRUCTURE, not by semaphore:

  - worker.py processes exactly ONE queue job at a time (no parallel
    jobs). This is the effective concurrency cap of 1.
  - relay_v2.py awaits each Telethon call sequentially inside a job.
  - The three crons run as tasks in the same loop but are sleep-bound;
    only one does network work per tick.

RISK: there is no bound on how many Telethon updates the userbot client
buffers while a long PDF upload blocks the loop. Telethon's internal
update queue can grow if @Gallery_DLBot sends many messages during a slow
upload. RECOMMENDATION: set Telethon's `flood_sleep_threshold` and keep
the client on a bounded update queue; monitor RSS during multi-GB PDF
jobs (see §6).

--------------------------------------------------------------------
4. SCRAPER THROTTLING / PAYLOAD CAPS
--------------------------------------------------------------------

Token buckets (nhentai_cache.py:69) are per-minute, keyed by bucket_id,
stored in TURSO (shared across processes — correct). User traffic always
wins over the background sweep because the sweep consumes the same
`galleries` bucket.

Rate-limit tracking uses TWO IN-MEMORY dicts in scraper_bridge.py:
  _RATE_LIMIT_CACHE   (scraper_bridge.py:140)
  _RATE_LIMIT_STRIKES (scraper_bridge.py:141)

  ⚠ FINDING (minor RAM leak): these dicts are keyed by cache_key and are
  only pruned on read (the ban-expiry check at :289/:466/:675/:804/:812).
  Keys that are never looked up again are never evicted. On a long-lived
  backend process with many distinct search keys this grows slowly.
  At ~100 bytes/entry it would take ~1M distinct keys to matter, so the
  practical risk is LOW, but a periodic sweep (or a functools.lru_cache
  with maxsize, or deleting expired entries inline) is a cheap fix.
  Severity: LOW.

Payload caps: search responses are bounded by per_page=25. The frontend
no longer accumulates (v12.16) so the BROWSER-side memory is now flat —
this was the user-visible win. Server-side payloads were already capped.

--------------------------------------------------------------------
5. IN-MEMORY CACHE CAPS / TTL / LEAK CHECKS  +  DB POOL
--------------------------------------------------------------------

Turso TTLs (nhentai_cache.py:57-61) — deliberately long, serve-stale:
  gallery:  30 days      search: 3 days      suggest: 3 days
  trending: 30 min       stale-grace: 7 days
These are TURSO rows, not RAM — no 512 MB impact. The long gallery TTL is
safe because gallery metadata is essentially immutable.

In-memory: only the two rate-limit dicts (§4) plus small per-request
locals. No lru_cache, no unbounded result cache in the request path.

Mongo pool (db.py:113-132): ONE process-wide MongoClient,
  maxPoolSize=20.
  ⚠ FINDING: maxPoolSize=20 is the default and is FINE for the worker
  (sequential), but 20 sockets x 2 processes x Atlas overhead is worth
  watching if the backend ever handles concurrent search bursts. Each
  idle pool socket is cheap (<1 MB), so this is not a RAM problem on
  512 MB. No change required. db.connect()/close() are lightweight
  handles over the shared client (db.py:24-27) — correct pattern.

--------------------------------------------------------------------
6. SAFETY IMPACT ON USER-FACING FUNCTIONALITY  +  RECOMMENDATIONS
--------------------------------------------------------------------

The crash with ~8 users online was a PEAK event, not a steady-state leak:
8 concurrent users each triggering search + detail fetches while the
details_prefetch_cron day-window pause (300s active-window) may not have
engaged fast enough. Three compounding factors:

  (a) details_prefetch_cron hydrating 25 details in one tick while real
      users were ALSO fetching -> same Turso bucket + same event loop.
  (b) the v12.15-and-earlier frontend accumulated every visited page in
      the DOM (100+ cards by page 4) — this is a BROWSER/WebView memory
      problem, NOT Render RAM, but it made the app feel like it crashed.
  (c) Render's 512 MB is shared by the uvicorn worker + the Mongo pool +
      Turso client; a large PDF relay in the worker spikes RSS.

RECOMMENDATIONS (ranked, cheapest first):
  1. KEEP the v12.16 strict pagination — it removes factor (b) entirely.
  2. Bound the two rate-limit dicts in scraper_bridge.py (evict expired
     entries on write, or cap length). 15-minute fix. LOW effort.
  3. Lower DETAILS_SCRAPER_MAX_PAGES_PER_TICK stays at 1; raise
     DETAILS_SCRAPER_DAY_REST_SEC from 5s to ~10s so the day sweep yields
     more to real users. Env-only change, no redeploy.
  4. Add a lightweight /healthz RSS log (or Render's built-in metrics)
     so the next peak is measured, not guessed.
  5. If peaks persist: split details_prefetch_cron OUT of the worker
     service into its own Render cron job so its memory is isolated from
     the user-facing backend. This is the only structural change worth
     considering, and only if 1-4 don't suffice.

--------------------------------------------------------------------
7. DOES RENDER DOWNLOAD IMAGES FROM TURSO THEN UPLOAD THEM TO THE
   MINI-APP?  (actual data path, from the code)
--------------------------------------------------------------------

NO. Render never proxies image bytes for the mini-app grid.

  - Turso stores METADATA ONLY (JSON payloads under gallery:/search:
    keys) — nhentai_cache.py put()/get() handle JSON text, never binary.
  - The search route (routes/search.py) returns JSON items whose `cover`
    field is a URL STRING built by scraper_bridge._thumb_url_from_item:
        https://t.nhentai.net/galleries/<media_id>/cover.<ext>
    (scraper_bridge.py:177 _T_CDN, :254 the f-string). hf_scraper.py
    similarly builds t3/i.nhentai.net URLs (:645, :653, :684).
  - Grep for StreamingResponse / FileResponse / iter_content / redirect
    across ALL routes and services returns ZERO matches. There is no
    image-proxy endpoint in the backend.
  - The frontend renders `<img class="card-cover" src="<that URL>">`
    (components/card.js via search.js renderCard). The BROWSER / Telegram
    WebView then fetches the image bytes DIRECTLY from nhentai's CDN
    (t/i.nhentai.net), completely bypassing Render.

So the image data path is:
    nhentai CDN  -->  user's browser/WebView      (image bytes)
    Render       -->  user's browser               (JSON with the URL only)
    Turso        -->  Render                       (cached metadata JSON)

Render's network and RAM are NOT in the image path at all. The only place
Render touches binary media is the WORKER's PDF relay (relay_v2 uploads
the PDF to Telegram via Telethon) — and that is one job at a time.
